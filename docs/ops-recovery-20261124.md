## 1. 갱신 승인 후 미지급과 구독 상태 복구

운영에서 10/12·11/8·11/12 각 9,900원, 총 29,700원 승인 기록 3건은 장부 `succeeded / pending`, 연결된 사용량 지급·환불 기록이 없고 구독은 이후 취소됐다. 결제사 현재 상태는 미확인이다. 따라서 DB 승인 기록만으로 자동 지급하거나 환불하지 않았다.

확인된 코드 결함:

1. 결제 결과 저장 후 구독 상태 저장 전에 중단되면, 다음 실행은 이미 실패한 시도를 `wait`로 끝내 구독이 `active`, 재시도 횟수 0인 채 남는다. 운영의 연체 18건은 실패 8건·결과 미확정 10건인데 이 상태였다.
2. 승인 후 사용량 지급 저장이 실패해도 공통 예외 처리에서 구독을 결제 실패 상태로 바꿀 수 있었다.
3. 취소·만료 구독은 갱신 후보에서 빠져 승인 후 미지급 기록이 자동 점검에서 누락됐다.

수정:

- 현재 구독 기간의 실패·미확정 장부를 확인해 구독 상태를 복구한다. 승인된 장부는 실패로 취급하지 않는다.
- 구독 잠금을 얻은 뒤 장부와 대상 기간을 재확인한다. 동시 승인·갱신 뒤 오래된 실패로 되돌리지 않는다.
- 미확정 결제는 재청구하지 않고 원장 조회 대상으로 유지한다.
- 종료 구독의 승인·미지급 기록은 검토 대상으로 표시한다. 지급 기록이 이미 있으면 표시하지 않으며, 취소 복원·재청구·자동 환불은 하지 않는다.
- 공급자 승인 후 지급 오류는 `fulfillment_pending`으로 구분한다.

검증: 기존 코드에서 복구 회귀 테스트 6개 중 5개 실패, 수정 후 6개 통과. 실제 SQL을 로컬 PGlite에서 실행해 지급/기간/장부의 원자성, 중복 지급 방지, 지급 실패 시 롤백, 취소 보존, 기존 지급 제외 등 5개 통과. 결제 API는 모두 대역으로 차단했다. 실제 결제사의 승인·취소 상태를 검증한 결과는 아니다.

## 2. 정기결제 300초 시간 초과

근거: 20:07~20:12 KST 실행도 `Vercel Runtime Timeout Error: Task timed out after 300 seconds`. 요청 `8mlwk-1795518442126-de5b09c0e53d`.

같은 시간대 갱신 장부는 20:08 승인 1건, 20:10~20:12 미확정 조회 5건이 갱신됐다. 실행 중 DB 조회에서 장기 잠금 대기는 관찰되지 않았다. 이 자료만으로 특정 HTTP 호출이나 SQL을 시간 초과의 단일 원인으로 확정할 수는 없다.

기존 코드에는 이전 결제 처리의 90초 예산만 있고, 이후 Toss 후보 최대 100개 순회에는 전체 시간 제한이 없었다. 새 후보는 전체 요청 260초를 기준으로 새 결제를 완료할 여유가 부족하면 다음 항목을 시작하지 않는다. 이미 시작한 결제를 Promise.race로 버리지 않는다. 후보는 오래 처리되지 않은 항목부터 정렬하고 단계/항목의 시작·종료·소요 시간을 기록한다.

이는 순회 누적 시간 초과를 제한하는 수정이다. 운영에서 모든 300초 초과가 해결됐다는 검증은 아니다. 배포 후 단계별 기록 확인이 필요하다.

## 3. 일반 YouTube 수집 실패

운영 프로젝트 39605, Batch `c33654f3-f95d-4f46-acf1-6a4fd6f377b8`는 애플리케이션 실패를 처리한 뒤 정상 종료해 Batch `SUCCEEDED / exit 0`이었다. 영상 제작 성공과 다르다.

기존 로그: `ingestion_work_failed ... attempt_count:1 retryable:false error_type:IngestionError`; `project_run_failed ... error_code:youtube_extractor_failed`.

실패 분류기에는 정제된 upstream 상세가 있었지만 일반 프로젝트 경로의 종료 처리에서 버렸다. 다음과 같이 수정했다.

- 분류된 수집 상세를 실패 로그와 `video_jobs.error_details`에 보존한다.
- 최종 상태가 실제 실패일 때만, 같은 오류 코드인 작업에 종료 처리와 함께 저장한다.
- URL·비밀값을 제거한 upstream 원인을 남긴다. 원문 명령·프록시 비밀번호는 기록하지 않는다.
- 제한 콘텐츠와 봇/429 문구가 함께 있어도 콘텐츠 제한을 먼저 적용해 경로 재시도를 막는다.

관련 수집/종료 테스트 52개 통과. 과거에 버려진 상세를 복구한 것은 아니므로 기존 실패 전부를 IP 차단, 토큰 오류, yt-dlp 버전 문제로 단정하지 않는다.

### 형식 수집 실패는 추가 원인 확인 필요

최근 로그에서 `ranking_download_failed`를 작업별 중복 제거하면 40건 중 39건이 `format_unavailable`, 1건이 `restricted_or_unavailable`이었다. 이는 최종 렌더 실패 수와 분모가 다르다.

기존 기록은 정보 조회와 미디어 다운로드를 구분하지 못했다. 새 후보는 `metadata / media / unknown`의 제한된 단계값을 내부 작업 상태와 웹 로그로 전달한다. 원문·인증값은 기록하지 않는다.

실패 이력이 있는 공개 영상 2개를 로컬 직접 연결로 메타데이터만 비교했다. yt-dlp 2026.7.4와 2026.11.23 모두 성공했고 새 버전에서 영상 형식 수는 16→25, 19→31로 늘었다. 운영과 같은 프록시/PO 제공자 환경의 재현이 아니므로 업데이트로 해결됐다고 볼 수 없다. 운영 버전 핀은 바꾸지 않았다. 새 버전은 격리 설치했고 공유 가상환경은 변경하지 않았다. 버전 변경 근거 확인은 [공식 릴리스](https://github.com/yt-dlp/yt-dlp/releases)를 사용했다.
