## Monthly entitlement and compatibility

A completed canonical transaction is validated against its exact price/currency/billing frequency. Each package creates one grant per calendar month, with future `valid_from` dates. Existing usage display and SQL reservation functions enforce `valid_from <= now < expires_at`, so a six-month payment never exposes all six quotas immediately. Month-end anchors are clamped independently (Jan 31 → Feb 28/29 → Mar 31). There is no new quota cron or always-on infrastructure.

The provider billing period and next billing date cover the entire prepaid term. The legacy `billing_cycle='monthly'` field retains its existing recurring-subscription exclusion/uniqueness semantics; provider price frequency is authoritative for payment cadence. Domestic renewal jobs already exclude Paddle.

Migration `202609260020_paddle_packages.sql` adds six inactive-for-domestic-catalog plan rows, widens only the existing code constraint without validating legacy data, and adds the private/RLS-protected `paddle_payment_grants` mapping. It backfills old one-grant payments and retains `paddle_payments.grant_id`. Refund handling also falls back to the old pointer for a monthly payment created by the previous release during deployment.

Approved partial refunds proportionally reduce every monthly allowance; full refunds and immediate cancellation revoke unspent current/future grants while retaining consumed/reserved ledger floors. Scheduled cancellation retains paid-through access. Renewals and duplicate notifications cannot double-grant a period. The prior safe unfinished-checkout replacement behavior is retained for term/currency changes.
