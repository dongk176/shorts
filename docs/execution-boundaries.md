# 운영·테스트 작업 대상 확인

이 문서는 작업 대상을 확인하는 절차다. 배포 권한이나 비용 승인을 새로 주지 않는다.
현재 대화에서 승인된 범위는 이어서 적용하고, 확인되지 않은 연결로 원격 변경을 진행하지 않는다.

## 이미 승인된 작업은 이어서 진행

2026-09-09 최신 사용자 정정: **이미 요청한 수정·테스트에 필요한 종량제 사용료는
매번 비용을 묻지 않고 진행한다.** AI 호출·비교, 전사, 빌드, 테스트 워커 실행,
영상 제작·댓글 재생성·렌더·편집·다운로드, 필요한 임시 보관·전송, 제한된 재시도와
종료 정리가 포함된다. 기존 서비스와 승인된 작업 대상을 사용한다.

예전의 1,000원 기준과 10,000원 실행 묶음·누적 재승인 기준은 이 일상 테스트에
적용하지 않는다. API 호출·재시도·재빌드·대화 턴마다 비용 승인 질문을 만들지 않는다.
과거 검토 문서와 실행 기록의 “비용 승인 대기”는 당시 기록이며 최신 규칙보다 우선하지 않는다.

**새로운 고정비·정기 결제 약정이 생기거나 증가할 때는 먼저 묻는다.** 새 유료 Supabase/DB
프로젝트, 구독, 유료 요금제 업그레이드, 사용하지 않아도 청구되는 ALB·상시 서버가 해당한다.
월 결제가 아니라 시간당 청구되는 자원도 유휴 고정비가 생기면 여기에 포함된다.
동일한 자원·비용 범위에 이미 받은 승인은 유지한다.

테스트 비용 관리는 에이전트가 맡는다. 실행 전에 합리적인 예상치를 기록하고, 실행 시간·
재시도·자원 크기를 제한하며, 사용량을 확인하고 종료 시 약속한 OFF 상태로 복원한다.
예상치가 불확실하면 작은 범위로 나눠 검증하며 스스로 제한한다. 내부 예산·토큰·빌드 횟수는
통제와 기록을 위한 값으로, 필요한 수정·재검증에 맞춰 조정할 수 있다. 이를 사용자에게
재승인을 요구하는 조건으로 사용하지 않는다. 이후 사용자가 특정 작업에 명시한 별도 상한은
지킨다. 기존 서비스의 필요한 종량제 보관료도 테스트 사용량에 포함하며, 이전 프로젝트가
참조하는 이미지·워커는 보존한다. 무관한 구매나 무기한 부하 시험을 허용하는 규칙은 아니다.

환경 식별·권한·운영 분리·워커 버전·배포 검사는 그대로 유지한다. 이미 승인된 데이터·AI
공급자의 사용 범위도 이어서 적용한다. 실제 자동 승인 심사의 거절을 문서나 승인 기록을
고쳐 해제한 것으로 처리하지 않는다. 다른 사유로 도구가 차단하면 그 실제 사유를 설명하며,
비용 승인을 다시 받아야 하는 것처럼 안내하지 않는다.

## 시작할 때

1. 사용자의 현재 범위를 `lab`, 운영 조회, 승인된 운영 변경으로 구분한다.
   현재 폴더가 무엇인지와 로컬 변경/조회/원격 변경 중 무엇을 할지 짧게 알린다.
2. `git rev-parse --show-toplevel`, `git branch --show-current`, `git status --short`,
   `git worktree list`로 실제 체크아웃과 기존 변경을 확인한다. 관련 폴더의 `AGENTS.md`도 읽는다.
3. 실행할 명령, 설정 파일, 인증 파일이 어느 환경을 가리키는지 확인한다.
   비밀값을 출력하거나 운영 `.env` 전체를 lab에 복사하지 않는다.

2026-09-08 기준 lab 도구는 `.tmp/test-platform-20260906` 작업트리의
`test-platform/`에 있다. 바깥 프로젝트 폴더에는 아직 이 도구가 없을 수 있다.
이 위치는 탐색 단서이며, 최신 브랜치·배포 증거가 아니다. 다른 작업의 변경을 덮어쓰거나
전체 폴더를 복사하지 말고 작업트리와 설정을 확인한다.

로컬 소스, 이미 빌드한 이미지, AWS에 등록된 워커, 웹이 실제 사용하는 워커는 서로 다르다.
커밋했다고 배포된 것이 아니고, `ACTIVE` 워커라고 현재 웹에 배정된 것도 아니다.
현재 배포 버전을 이 문서에 고정하지 않는다. 작업 당시 실제 조회와 릴리스 등록값을 사용한다.

## 로그인 전에 테스트 구성부터 확정

2026-09-12 사용자 정정: **lab과 운영은 별도로 개발·배포하는 환경이다. 같은 기능이나
최신 버전이라고 가정하지 않는다.** 테스트용 계정이 있다는 이유만으로 기존 lab 웹이
운영 변경의 검증 대상이 되는 것은 아니다.

로그인을 요청하거나 원격 변경을 시작하기 전에 다음을 확인하고 짧게 기록한다.

1. **검증할 코드:** 실제 작업트리·브랜치·커밋과 변경 범위. 운영 변경은 현재 승격된
   운영 커밋을 기준으로 한다. lab의 개발 브랜치를 운영 기준으로 대신하지 않는다.
2. **실행할 환경:** 로컬 격리 검증인지, 승인된 lab 자원의 별도 후보인지, 운영 배포
   후보인지 구분한다. 코드의 출처와 연결할 계정·프로젝트·DB·스키마를 따로 설명한다.
3. **관련 차이와 의존성:** 실제 배포 버전, 대상 기능, 필요한 API·DB 구조·워커·환경별
   보호 설정을 대조한다. 기존 lab에 운영 기능의 기반이 없으면 그 lab 웹에서의 테스트로
   운영 검증을 대신하지 않는다. 별도 후보를 쓰더라도 환경별 보호장치와 호환성을 확인한다.
4. **검증 범위와 한계:** 어떤 동작을 확인하며 무엇이 미확인인지, 어떤 인증·서비스가
   실제로 필요한지 정한다. 로그인은 이 구성에 필요한 경우에만 요청한다.

가능한 로컬 검사와 기존 유효한 인증의 읽기 조회를 먼저 사용한다. 특정 사실을 확인하는
데 새 인증이 필요하면 그 사실을 미확인으로 표시하고, 필요한 조회와 계정을 설명한 뒤
해당 로그인만 요청한다. 확인 전에는 그 사실에 의존하는 변경을 하지 않는다.

**lab 원격 변경 전의 경계 검사를 모든 운영 작업의 선행 조건으로 확대하지 않는다.**
로컬 화면·언어 판정 검사만 필요한데 AWS 워커 로그인부터 요구하지 않는다. 반대로
실제로 lab 원격 변경을 선택했거나 요청받았다면 기존 `lab:boundary`와 해당 작업의
사전 검사를 그대로 지킨다. “lab에서 테스트”라는 요청도 코드·기능·DB 구조가 호환된다는
증거는 아니므로 먼저 구성을 확인한다.

두 환경의 버전을 맞추려고 작업 범위를 벗어난 기능 동기화, lab 브랜치 전체의 운영 통합,
기존 lab 웹 덮어쓰기, 운영 계정·DB·비밀값 복사를 하지 않는다. 테스트 결과에는 실제
검증한 소스와 설정을 연결하고 후보와의 차이를 남긴다. 운영 적용 전에는 현재 운영
기준의 **실제 배포 후보**를 다시 검증하며 기존 보호 경로·동일 후보 승격 규칙을 유지한다.

## lab 원격 변경 전 검사

lab 도구가 있는 확인된 작업트리에서 실행한다.

```sh
npm run lab:boundary
```

이 명령은 등록된 lab 설정을 검증한 뒤 다음을 **읽기 전용**으로 확인한다.

- 실제 AWS 로그인 계정과 실제 Vercel 프로젝트 ID/이름.
- 테스트 DB 주소·역할 및 실제 권한 분리. 기존 스키마·소유자 접근 불가 여부.
- 생성 워커 5개 경로의 현재·등록된 이전 버전: 정확한 ARN, 이미지 digest,
  내부 소스/이미지/글꼴 값, 테스트 역할·비밀값 참조·저장소·대기열·실행 사양.
- 편집 워커 등록 목록의 현재·이전 버전: 정확한 ARN, 활성 상태, 이미지·소스·글꼴.

AWS 계정 확인에 실패하면 AWS 자원 조회를 진행하지 않는다. 독립적인 Vercel/DB
검사는 계속하며 접근할 수 없는 항목은 미확인으로 남긴다. 실패 시 종료 코드는 1이다.
큐가 `DISABLED`여도 경계 확인은 가능하다. 이 명령은 자원을 켜거나 작업을 제출하지 않는다.
로컬에는 검사 결과와 일시적인 중복 실행 방지 파일만 기록한다.

검사 성공은 그 시각에 위 항목을 확인했다는 뜻이다. `readyForPaidJobs`는 항상 `false`다.
인증 만료, 작업트리·환경 설정·워커 등록 변경 뒤에는 다시 확인한다.
인증이 없으면 전용 테스트 로그인만 복구하고, 기본 AWS 로그인이나 운영 인증으로 대체하지 않는다.
실패 원인을 없애려고 계정 ID, DB 스키마, 허용 목록 또는 안전 검사를 느슨하게 바꾸지 않는다.

## 배포·제작에서 추가로 유지할 검사

- `lab:boundary`는 업로드 서버, 제출 Lambda의 실제 허용 목록, 후보 웹의 실행 설정,
  DB에 저장된 모든 프로젝트의 워커 참조를 전부 검증하는 명령이 아니다.
  기존 배포 도구의 작업별 사전 검사와 인증된 후보 웹의 제작 준비 검사를 유지한다.
- 실제 제작 전에는 웹의 5개 워커 대상 fingerprint, lab 등록값, AWS 실조회가 일치해야 한다.
  업로드 서버와 편집기 릴리스도 각자의 사전 검사를 통과해야 한다.
  페이지 200 응답이나 빌드 성공만으로 제작 가능하다고 판단하지 않는다.
- 운영 워커와 lab 워커의 버전은 달라도 된다. 각 환경 안에서 저장된 작업 대상과
  제출기가 허용하는 대상, 실제 실행 워커가 맞아야 한다. 오류를 숨기려고 운영 값을 바꾸지 않는다.
- 이전 대상 제거 전에는 해당 프로젝트·재시도·편집 요청의 참조를 확인한다.
  현재 등록 목록 검사만으로 오래된 프로젝트의 호환성이 증명되지는 않는다.
- `lab:doctor`는 실행 준비 검사이므로 큐 OFF에서 실패할 수 있다. 단순 확인을 위해 켜지 않는다.
  실제 제작은 기존 비용 승인과 제한 시간 안에서 진행하고 종료 시 승인된 OFF 상태를 복원한다.
- `infra:deploy-control-plane`, `vercel:sync-project-targets`, 이름에 `production`이 붙은
  배포·동기화 스크립트를 lab 작업의 대체 수단으로 쓰지 않는다. 이름만 믿지 말고 본문도 읽는다.
  Vercel의 `production` 배포 유형은 프로젝트 내부 채널 이름이므로 대상 프로젝트 ID까지 확인한다.

자동 적용을 가정하지 않고 `AGENTS.md`에서 명시적으로 연결한다. 새 작업트리에도 이 파일을
포함하고, 이미 실행 중인 다른 작업에는 변경된 지침을 다시 읽도록 알려야 한다.
세부 탐색 순서는 [OpenAI의 AGENTS.md 안내](https://learn.chatgpt.com/docs/agent-configuration/agents-md)를 따른다.

문서와 이 검사 명령은 임의의 AWS/Vercel 명령을 운영체제 수준에서 차단하지 않는다.
기존 계정 분리·제한된 인증·DB 역할·제출기 허용 목록을 함께 유지해야 한다.
검사를 통과시키기 위해 이 권한 경계를 넓히거나 자동 승인 거절을 우회하지 않는다.
