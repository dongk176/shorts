# 레퍼럴 월별 정산

## 운영 기준

- 한국시간 회차 발생 월의 1일~말일 실적을 익월 10일부터 수동 지급한다.
- 확정 매출은 회차 발생 후 정확히 7일이 지난 환불 반영 순매출이다.
- 선불 상품의 기존 월별 회차, 결제 당시 수익률, 원 단위 절삭 계산은 유지한다.
- 두 화면의 기본 조회 월은 전월이다. 매월 1일 조회 기본값만 바뀌며 원장은 삭제하거나 초기화하지 않는다.
- 주말·공휴일에도 예정일은 10일이다. 자동 이체는 실행하지 않는다.
- 고객 환불액 산정과 첫 작업 완료 여부에 따른 1개월 공제 조건은 변경하지 않는다.

## 공통 조회와 기록

`web/lib/referral-settlement.ts`가 월 경계, 지급일, 과지급 조정과 상태를 계산한다.
`referral-settlement-server.ts`가 관리자·파트너·CSV의 원장 조회를 담당한다.
파트너 화면과 CSV는 읽기 전용 repeatable-read 조회로 합계와 거래 상세의 환불 시점을 일치시킨다.
조회는 지급 기록을 만들지 않는다.

`referral_payouts`에 실적 월, 지급 예정일, 매출·수익·조정액·회차별 계산 snapshot을 추가한다.
파트너별 같은 실적 월의 활성 기록은 하나만 허용한다. 기존 RLS와 계좌 암호화는 유지한다.
과거 수동 송금은 없다는 운영 확인을 전제로 하며, 임의 기간의 기존 활성 기록이 발견되면 마이그레이션이 중단된다.

## 관리자 처리 순서

1. 실적 월과 지급일, 계좌, 최종 지급 대상액을 확인하고 **지급 준비**한다.
2. 최신 환불 반영 금액을 고정하고 해당 월 회차에 금액을 배정한다.
3. 준비 후 금액이 달라지면 화면에 경고한다. 아직 송금하지 않았다면 **준비 취소** 후 다시 준비한다.
4. 외부 은행에서 준비된 금액을 송금한 뒤 **지급 완료**에서 그 금액과 이체 확인값을 확인한다.
5. 완료 처리 시 준비된 금액을 다시 계산하거나 줄이지 않는다. 실제 송금액과 회차 snapshot을 보존한다.

지급일 전, 계좌 미등록, 조정 후 0원인 경우 준비할 수 없다. 이전 기간 입력은 정확히 한 달인 경우만 실적 월로 변환한다.
서버는 파트너를 먼저 잠근 뒤 지급 처리하며 요청 식별자와 월별 활성 고유 제약으로 동시 요청을 막는다.

## 환불 조정

기존 환불 회차 계산을 그대로 사용하므로 1개월분을 남긴 환불은 해당 회차 수익을 유지한다.
예외적 전액 환불 등으로 이미 지급·준비된 금액이 현재 권리 금액보다 크면 그 차액을 **이전 지급분 환불 조정**으로 표시한다.
지급일이 도래한 미정산 월에 오래된 순서로 차감하며, 해당 월 금액을 넘는 조정은 다음 지급 대상으로 넘긴다.
지급일이 오지 않은 다른 월의 수익은 지급액을 보충하는 데 사용하지 않는다.
조정 후 지급한 월의 차액을 함께 계산하므로 같은 환불을 두 번 차감하지 않는다.
과거의 양수 미지급 실적은 항상 원래 실적 월에 남는다.

## 검증

`web/lib/referral-settlement.test.ts`는 한국시간 자정, 7일/10일 경계, 윤년·연말, 과거 미지급과 조정 이월을 검증한다.
`web/lib/referral-payout.integration.test.ts`는 실제 PostgreSQL에 기존 원장 migration과 추가 migration을 적용하여 선불·환불 trigger, 금액 고정, 취소·재준비, 중복 요청, 결제 시점 수익률과 절삭, 파트너 격리, CSV 합계를 검증한다.
통합 테스트는 `REFERRAL_TEST_DATABASE_URL`이 localhost의 `referral_test`인 경우에만 파괴적 초기화를 허용하며 운영 DB에는 실행하지 않는다.

배포 시 `202609100002_referral_calendar_payouts.sql`만 추가 적용한다. 기존 원장 합계와 월별 합계를 읽기 전용으로 대조하고, 최신 운영 기준의 경로 및 5개 작업 대상 검사에 통과한 무별칭 후보를 그대로 승격한다.
